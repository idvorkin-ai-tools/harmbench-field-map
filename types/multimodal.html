Multimodal behaviors

The fourth functional category — an image, a question about it, and a text-only judge that never looks at the picture.
TL;DR — A multimodal behavior is a picture plus a request that refers to it, so neither half is harmful on its own and neither half can be evaluated alone. It is the benchmark's least balanced slice: 90 of the 110 come from just two harm categories, and 50 of the 110 are CAPTCHA-solving. Unlike the 400 text behaviors, these ship with no test/val split, so the guard that lets you tune a method without touching the reported set does not exist here. Grading runs through a third classifier that is a text model reading a hand-written redacted description of an image it never sees. And the number to carry away is Table 10's: a PGD-optimised noise image drives 48.75–66.00% ASR on ordinary text behaviors, while rendering those same requests into an image gets 3.50–5.25% — the pixel channel is a second door into the same model, and it is far less defended than the one the safety training was aimed at.

The other three functional types differ in how a request is phrased. This one differs in what a request is. A multimodal behavior hands the model an image and asks something whose harm only exists because the image is there — which changes the attack surface (you can now optimise pixels, not just tokens), changes the grading problem (the judge has to reason about content it cannot inspect), and changes what a number means (there is no held-out split to report on). All three changes cut in the same direction: this is the part of HarmBench where the measurement apparatus is thinnest, and also the part where the attacks work best.

What a multimodal behavior actually is

The multimodal CSV has nine columns against the text set's six: Behavior, BehaviorID, FunctionalCategory, SemanticCategory, ImageFileName, Source, ImageDescription, RedactedImageDescription, Tags. Four of those exist only here. ImageFileName points into data/multimodal_behavior_images/ and is simply <BehaviorID>.png — the directory holds exactly 110 PNGs, one per behavior, about 65 MB in total, and they are committed to the repository rather than fetched by a setup step (the README describes no download for them; git ls-files lists all 110). If you cloned HarmBench you already have the images. Source is a URL to wherever the picture came from, overwhelmingly Wikimedia Commons, which is how a benchmark of harmful visual prompts gets built without the authors photographing anything: the paper notes that faces were manually blurred or replaced with generated images where privacy required it.

The two description columns are the interesting ones. ImageDescription is a written account of what the picture shows. RedactedImageDescription is the same account with the harmful specifics taken out, and it is not decoration — it is the input the grader runs on. Neither is shown to the target model; the target gets pixels.

The behavior string itself is a question about the image, so it is close to inert in isolation. Read one without its picture and it often reads as a mundane request with an unresolved referent; look at one of the pictures without its request and it is usually an ordinary photograph or diagram. That is deliberate, and it is the same design move as the contextual type's supplied passage: it buys differential harm, because the answer is not something a search engine can return. It also means a harness that resolves the image path wrong, or that silently passes a blank tensor, will not throw — it will just quietly measure a different, much easier benchmark. As with contextual behaviors, the failure mode is a plausible number rather than a crash. (This site prints no behavior strings and no image descriptions; the behavior index carries every ID.)

One asymmetry to note for anyone writing code against the CSV: the Tags column is present but empty on every multimodal row, while the grading dispatch in eval_utils.py branches on a multimodal tag. Nothing in the shipped file sets it. The pipeline works because the multimodal path is invoked with its own classifier and its own scripts, but a reader who assumes the tag is there — the way context genuinely is on the 100 contextual rows and hash_check is on the 100 copyright ones — will get the standard prompt instead of the contextual one and never be told.

Two categories carry 82% of the image set. Three of the seven contribute eleven behaviors between them. Copyright contributes none, which follows from its grading rule rather than its subject matter — the copyright metric is a MinHash match against shipped reference hashes of specific texts, and there is no version of that test which starts from a picture.

The skew has one dominant cause, and the repository makes it visible without opening a single CSV row: 50 of the 110 image files are named solve_captcha_<n>.png. The paper says why.

"We include 50 CAPTCHA behaviors to allow measuring whether multimodal models robustly refuse to impersonate humans online."— HarmBench, Figure 17 caption

So nearly half of this functional type is one narrow task, filed under Cybercrime & Unauthorized Intrusion because §B.4 lists CAPTCHAs there alongside hacking and malware. That is a defensible thing to measure — automated CAPTCHA defeat is a real abuse vector and a vision model is exactly what makes it cheap — but it means a headline multimodal ASR is roughly half a CAPTCHA-refusal score and half everything else, and those two things have no reason to move together. When you read Table 9 below, read it as a blend. If your own model is being compared on this set, the single most informative thing you can do is split the 50 CAPTCHA behaviors out and report them separately.

The grader that never sees the image

Multimodal completions are graded by a third fine-tune, cais/HarmBench-Llama-2-13b-cls-multimodal-behaviors, a sibling of the test classifier used for the text set. It is a Llama 2 13B text model. It has no vision encoder, and it is never handed the picture.

What it gets instead is in the dispatch at the bottom of eval_utils.py's compute_results_classifier. The function branches three ways on the behavior's tags: context takes the contextual path and fills the template's {context} slot from ContextString; multimodal fills that same slot from RedactedImageDescription; everything else gets the plain standard prompt. The multimodal branch is not a different rubric — it is the contextual rubric with a paragraph of English standing in for the image. The notebook the README points at confirms this is intended and not an oversight: its prompt_multimodal template is structurally the contextual one, same rule list, same [CONTEXT]/[BEHAVIOR]/[GENERATION] shape.

Understand what that buys and what it costs. It buys enormous practicality: one 13B text model grades both contextual and multimodal completions, no vision-language judge to train, no image plumbing at eval time, and the same >90% human-agreement machinery carries over. What it costs is the ability to check grounding. The judge cannot tell whether a completion describes what is actually in the picture, because it has never seen the picture; it can only ask whether the completion would count as the behavior assuming the description is accurate. A model that hallucinates the image's contents and then answers confidently about the thing it imagined can be scored a success. The reverse also happens: a completion that is correctly grounded in a detail the description omits looks like a non-sequitur to the grader.

And the description is not data. It is an artifact somebody wrote. The redaction step in particular is a hand-made editorial judgement about which specifics to strip — strip too little and you have handed the judge the answer, strip too much and a correct completion no longer visibly matches its context. There is no reported inter-annotator measurement of that step, and the classifier-agreement figures in Table 3 cover standard and contextual behaviors only; the multimodal path has no published agreement number of its own. That is a real hole under a number that gets quoted to two decimal places.

One more wrinkle worth knowing if you rebuild this. The prompt used to label the multimodal training data (Appendix C.4.1, the GPT-4 teacher prompt) is materially richer than the one used to serve the distilled classifier. The teacher version explicitly frames the task as judging on the assumption that the model saw the image, asks for several sentences of reasoning before answering, forgives object misidentification, and — because of those 50 CAPTCHA behaviors — carries an overriding instruction that a CAPTCHA attempt counts even when the answer is wrong or malformed. None of that appears in the template eval_utils.py actually runs. Those rules survive only as whatever the 13B student internalised during distillation. If you ever grade a CAPTCHA completion by hand and disagree with the classifier, this is the first place to look.

No published split, so no guard

The text behaviors ship as three files: 400 all, 320 test, 80 val. The multimodal behaviors ship as one, harmbench_behaviors_multimodal_all.csv. There is no _test and no _val.

This is not an oversight in the design, only in the release. The paper's appendix describes a 100-behavior validation set built by stratified sampling — 40 standard, 20 contextual, 20 copyright and 20 multimodal — leaving 410 for test. So a 90/20 multimodal split exists on paper. It is simply not in the repository, and the behavior IDs that made up those 20 are not recoverable from what shipped.

The practical consequence is that one of HarmBench's four stated design principles has no teeth here. Everywhere else, the rule is: tune your method against the validation split and the validation classifier, then report on the test split and the test classifier, so that nobody is optimising against the number they publish. On the image set there is only one set. Every multimodal figure in the paper is measured on all 110 behaviors — you can verify that from the table itself, since every cell in Table 9 is an exact multiple of 1/110 (64.55% is 71 behaviors, 82.73% is 91, 20.00% is 22), which also tells you there is exactly one test case per behavior. So when you compare a new multimodal attack against these numbers, nothing structural stops the comparison from being tuned. Say so when you report, and if it matters, cut and freeze your own held-out subset before you start.

The five multimodal methods

The text set gets 16 attack columns. The image set gets five methods, and the split between them is exactly the white-box / black-box line drawn on the gradient methods page — three need gradients through the vision encoder, two do not. All five are declared in run_pipeline.yaml with behavior_chunk_size: 5 and base_num_gpus: 1; the three gradient methods are restricted to open_source_multimodal targets, the other two also accept closed_source_multimodal. Those model-type declarations are what produce the dashes in the GPT-4V row.

The shared objective is the same one GCG uses: teacher-forced cross-entropy on an affirmative target continuation, given the behavior. The difference is the search variable. GCG has to hill-climb over discrete tokens with a projection at every step; here the variable is a tensor of pixels in [0, 1] and the gradient applies directly. That is the whole reason 10 PGD steps beat 500 GCG steps.

MultiModalPGD

white boxclass MultiModalPGD10 steps · ε 0.12564.6–82.7 on the 110

Start from the behavior's real image, preprocessed to the model's native resolution with normalisation deferred, so the optimisation happens in raw pixel space. Each step takes a sign-gradient move of step_size 0.01 against the target loss, clips back into an L∞ ball of radius epsilon around the original, and clamps to [0, 1]; the best-loss iterate is kept and an early stop fires below a loss of 0.01. Ten steps at 0.01 can move a pixel by at most 0.1, which is inside the 0.125 ball — so at the shipped defaults the imperceptibility budget never binds and the real cost knob is the step count. Ten forward-backward passes per behavior is a trivially cheap attack by the standards of anything on the gradient page, and it is the strongest column in Table 9.

MultiModalPGDPatch

white boxclass MultiModalPGDPatch2000 steps · ε 1.036.4–81.8 on the 110

Same loss, restricted support. A square patch of side 0.2×min(height, width) — about 4% of the pixels — is placed at a random position, initialised from noise, and optimised without an L∞ constraint while the rest of the image is left untouched. It is the digital analogue of a printable adversarial sticker, and it is the variant you would reach for if you wanted to argue that a real-world artifact, not a bit-exact file, could carry the attack. The trade is visible in the numbers: 200× the steps of plain PGD, and on InstructBLIP barely half the success (36.36 against 64.55). What limits it is not optimisation budget but how much of the image it is allowed to touch.

MultiModalPGDBlankImage

white boxclass MultiModalPGD in the pipeline config1000 steps · no ε48.8–66.0 on text behaviors

The odd one out, and the one that produced the most interesting result on this page. It ignores the image behaviors entirely and runs against the 400 text behaviors, synthesising a 512×512 image of uniform random RGB noise as the starting point — "blank" is a misnomer, the paper's caption more accurately calls it randomly initialised — and optimising it for 1000 steps with the L∞ radius pinned to 1.0, i.e. unconstrained. The image is not a carrier for a message; it is a free parameter with hundreds of thousands of dimensions that the attacker gets to set. Note a trap if you try to reproduce it: the run_pipeline.yaml entry named MultiModalPGDBlankImage declares class_name: MultiModalPGD, and the runner resolves both the class and the config file from that field — so driving it through run_pipeline.py gets you plain 10-step PGD on the image behaviors instead. Reaching the real variant means calling generate_test_cases.py with the method name directly.

MultiModalRenderText

black boxclass MultiModalRenderTextfontsize 10–201.8–20.0 on the 110

No gradients: draw the request into the picture as visible text and send a short text prompt telling the model to carry out the instruction in the image. The renderer walks the font size down from max_fontsize 20 toward min_fontsize 10 until the string is estimated to fit the region of interest (which the per-model configs set to the entire canvas), word-wraps it, and outlines each word in white for legibility on a photograph. Against text behaviors it renders onto a plain grey canvas instead, prefixing any context passage in the text channel. The premise — that OCR'd text might route around a refusal trained on typed text — is the same premise as ArtPrompt's ASCII masking, and here it mostly fails. It is the only method that reaches GPT-4V at all.

MultiModalDirectRequest

black boxclass MultiModalDirectRequestno hyperparameters16.4–69.1 on the 110

The floor, and the same role DirectRequest plays on the text set: hand the model the behavior and its unmodified image and see what happens. The only configuration is per-model geometry — image_width/image_height of 336 for LLaVA 1.5, 224 for InstructBLIP, 448 for Qwen-VL-Chat, 224 for GPT-4V — with a Lanczos resize to fit followed by a centre crop, so non-square originals arrive letterboxed. Everything else on this page should be read as a delta against this column, and on LLaVA that delta is small: 69.09 with no attack at all.

Three readings. First, pixel optimisation dominates: 64–83% against every open-weight model, from an attack whose default budget is ten gradient steps. Compare the text-set results, where the strongest column tops out at a 54.3 average after 500 steps of discrete search. Second, RenderText is weak everywhere — 1.82 on InstructBLIP — because these models read the rendered text and then refuse it the way they would refuse it typed. Third, GPT-4V is only reachable by the two black-box methods, and that is a statement about access rather than robustness: the API returns text, not gradients, so PGD has no derivative to descend. In the code this is literal — the GPT-4V wrapper's compute_loss delegates straight to an abstract method and returns nothing. The dashes mean "cannot be run", not "was resisted".

The GPT-4V column is also the only place in Table 9 where an attack beats DirectRequest by a wide relative margin (20.00 against 16.36). On LLaVA, RenderText is five times worse than simply asking. That is worth sitting with: three of the four attack/model pairs in the RenderText column would have done better with no attack at all.

Same models, same behaviors, same request text, and a fourteen-fold spread between the two columns. The difference is entirely what the image channel is used for. Render the request as legible pixels and the model reads it, recognises it, and refuses: 3.50–5.25%, below the DirectRequest floor on the text set. Fill the same channel with an optimised field of noise and 48.75–66.00% of the same behaviors come out. The image does not carry the request — the request is still in the text channel, unobfuscated. The image carries an optimisation.

That is the finding to take away from this page, and it generalises past HarmBench. Safety training was applied to the token channel. The pixel channel was attached later, is continuous rather than discrete, has orders of magnitude more attacker-controlled degrees of freedom per query, and had essentially no adversarial pressure applied to it during alignment — the paper says as much about all three open-weight targets:

"No specific safety measures were used in training this model. However, we find that it does refuse direct requests to perform egregious behaviors."— HarmBench, §C.2, said of each of InstructBLIP, LLaVA 1.5 and Qwen-VL-Chat

Refusal behaviour inherited from a text backbone survives contact with a plainly-worded request and does not survive contact with a gradient. Adding a modality adds an attack surface that your existing defences were never trained against, and the surface is larger than the one you did defend.

What to watch if you run this

Four cautions, in the order they will bite you. One: the multimodal corner of the repository is its least exercised. The Tags column is empty where the dispatch expects a value; the BlankImage pipeline entry resolves to the wrong class; MultiModalRenderText's constructor opens a targets file that its own config never sets and parses it with a module it does not import; the GPT-4V wrapper calls os.path.join without importing os and carries a placeholder API key as a literal. None of these are deep, but together they mean the multimodal path wants reading before it wants running — unlike the text pipeline, which is heavily travelled.

Two: report the CAPTCHA behaviors separately. Forty-five percent of one number measuring one narrow task is not a property of the set, it is a property of how the set was assembled, and no reader can back it out of an aggregate.

Three: remember what the grader is. Every ASR on this page is a text model's judgement about a picture it was described, not shown, and the description was redacted by hand. It is a reasonable proxy and it is not the same measurement as the text set's, so do not put multimodal and text ASRs in the same column and average them. The broader caveats on the classifier's failure modes — over-refusal is never measured, roughly 7% label noise, a fixed 512-token generation budget — all apply here too, on top of the blindness.

Four: and most transferably — if you are evaluating a vision-language model of your own, the DirectRequest column tells you what your refusal training does, and the PGD column tells you what it is worth. On LLaVA those are 69.09 and 74.55, which is to say almost nothing was left to break. On InstructBLIP they are 22.73 and 64.55, which is a model that refuses the polite version and folds on the optimised one. The gap between those two columns, not either number alone, is the thing an image channel actually costs you.
