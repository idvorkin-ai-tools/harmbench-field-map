Running it: the four steps

The page that answers “what do I actually type” — and where the runner will quietly refuse to do what you asked.
TL;DR — HarmBench is a dataset you download and a pipeline you run. Behaviors, classifiers and copyright hashes ship; the test cases do not, and you pay for them in GPU hours, one set per (attack × target model) pair. Four scripts do the work — generate_test_cases.py, an optional merge_test_cases.py, generate_completions.py, evaluate_completions.py — chained by run_pipeline.py in slurm, local or local_parallel mode. The field that will surprise you is model_type: every method declares which types it accepts, and a model of the wrong type is skipped with a bare continue — no warning, just a missing column. And if your target is an OpenAI-compatible endpoint rather than OpenAI itself, you are patching Python, not editing YAML.

Almost every confusing thing about running HarmBench comes from one split: part of the benchmark is a download, part is a computation. The 510 behaviors are a download; so is the Llama 2 13B classifier, and so are the 100 MinHash pickles that grade copyright behaviors. The test cases are not. A test case is what an attack produced when pointed at a specific model, so there is one set per (method × target model) pair, and producing them is the expensive half. That is why the repo is small and the run is not.

What ships, and what costs you GPU hours

Three ways to get a number out, then, differing by roughly four orders of magnitude in cost. Download the precomputed test cases — the 10.4 GB HarmBench Results 1.0 archive on Zenodo (record 10714577, shipped with the 1.0 release) — and re-run only steps 2 and 3. Run only the cheap attacks, which do no optimisation and finish in minutes. Or run the gradient attacks, where the GPU-months live.

Reuse works because completions and results are keyed by target model while test cases are keyed by experiment, so any test-case set can be pointed at any model. That is the design, not a hack: it is how GCG-Transfer and TAP-Transfer exist as columns in Table 6 at all.

The four steps

Four scripts at the repo root, chained by JSON files. Each step reads the previous step's file and writes its own, so knowing the filenames is most of knowing the pipeline — you diagnose a bad run by finding which file is missing or short.

Step 1 — generate_test_cases.py

This is where the attack runs. The script loads a red-teaming class from baselines/, initialises it from configs/method_configs/<Method>_config.yaml, hands it a slice of the behavior CSV, and saves what comes back. Everything expensive on this page happens inside that one call: GCG's 500 optimisation steps, PAIR's attacker–target conversation, GPTFuzz's mutation loop.

The slice comes from --behavior_start_idx/--behavior_end_idx, or an explicit --behavior_ids_subset that overrides them — the right tool for filling gaps after a failed job. Single-behavior methods write to {save_dir}/test_cases_individual_behaviors/{behavior_id}/test_cases.json, beside a logs.json and a method_config.json recording the exact hyperparameters, the pinned transformers/vllm/ray/fastchat versions, and any API token masked to its last four characters.

Step 1.5 — merge_test_cases.py

Step 1.5 exists because of how step 1 is parallelised. The base class states the contract in its docstring: the only requirement on save_test_cases is that running merge_test_cases afterwards yields a test_cases.json mapping behavior IDs to lists of test cases. Methods with no need to parallelise write that file directly and inherit a merge that is literally pass. Methods that do parallelise — one behavior or a small chunk per job, so a cluster can chew through 320 behaviors at once — scatter output across per-behavior directories, and the merge stitches it back.

Only three classes implement a merge. RedTeamingMethod is the no-op. SingleBehaviorRedTeamingMethod (GCG, PEZ, GBDA, UAT, AutoPrompt) unions the per-behavior directories, asserting no ID appears twice. EnsembleGCG is the interesting one, and the reason its entries carry behavior_chunk_size: all_behaviors: it optimises one adversarial string jointly against every behavior at once, so there is nothing to chunk and nothing to merge along the behavior axis. But it has a second axis — GCG-Multi and GCG-Transfer declare run_ids: [0,1,2,3,4], and the merge concatenates test_cases_{run_id}.json so each behavior ends up with five test cases and an ASR averaged over five independent optimisations. Same script, different seam.

A merge that finds a hole does not complain. SingleBehaviorRedTeamingMethod.merge_test_cases skips any per-behavior file that does not exist, so a job that OOM'd or hit its 24-hour SLURM wall drops silently out of the merged file — and step 3 computes an ASR over whatever survived. Check the length of test_cases.json against your behavior count before trusting a number.

Step 2 — generate_completions.py

Take the merged test cases, send each to the target model, save what comes back at completions/{model_name}.json. Decoding is greedy and deterministic — do_sample=False on the HuggingFace path, temperature=0 on the vLLM and API paths — and the budget is max_new_tokens=512 for every experiment in the paper.

The code makes the 512 literal in a way the docs only hint at: pass anything else and run_pipeline.py redirects both completions and results into a {N}_tokens/ subdirectory, so non-standard budgets cannot be accidentally averaged with the published grid. It matters because the metric is “did the model produce the harmful artifact,” and an artifact needing 700 tokens to finish scores as a failure at 512.

Step 3 — evaluate_completions.py

The grading pass. It reads the behavior CSV (for tags and context strings) and the completions, then dispatches per behavior: the hash_check tag routes to MinHash, everything else to the Llama 2 13B classifier, run under vLLM at temperature=0.0, max_tokens=1 — the label is a single token. Output is results/{model_name}.json, one 0/1 label per test case.

Three mechanical details worth carrying. Step 3 re-clips every completion to 512 tokens using the classifier's own tokenizer, truncation_side="right", so even a longer completions file is graded on its first 512 classifier-tokens. ASR is a mean of means — success rate computed per behavior, then averaged — which matches a flat mean at one test case per behavior but not at GCG-Multi's five. And a behavior ID present in the completions but absent from the CSV you passed is skipped with a printed warning, which is how a completions file built from all 400 behaviors gets graded against the 80-behavior validation split.

Chaining it: run_pipeline.py

You rarely call the four by hand. scripts/run_pipeline.py reads run_pipeline.yaml, expands each method into per-model experiments, sizes each job's GPU request, and submits the chain:

python ./scripts/run_pipeline.py \
  --methods DirectRequest,PAIR,TAP \
  --models your_model \
  --behaviors_path ./data/behavior_datasets/harmbench_behaviors_text_val.csv \
  --step all --mode local_parallel \
  --cls_path cais/HarmBench-Llama-2-13b-cls

--step takes all, 1, 1.5, 2, 3 or 2_and_3 — that last being the workhorse for anyone using the Zenodo archive: skip generation, score an existing test-case set against a new model. --mode takes three values, and they are genuinely different execution models, not verbosity levels.

  • slurm — the intended path. Each chunk becomes an sbatch job, steps wired with --dependency=afterok: on the previous step's job IDs, so the whole DAG goes in with one command. The hard-coded wall times say what the authors expected: 24 hours for step 1, ten minutes for the merge, five hours each for completions and evaluation.
  • local — sequentially on this machine. Fine for a smoke test, useless for a real grid. Steps 1.5, 2 and 3 run under capture_output=True, so they produce no live output at all — a long silent step 2 is not necessarily a hung one.
  • local_parallel — Ray across one box's GPUs, marked experimental in the source. It registers a custom visible_gpus resource sized to torch.cuda.device_count() and sets CUDA_VISIBLE_DEVICES per subprocess: cluster-shaped parallelism without installing SLURM, and the right mode for a single 8×A100 machine.

One path detail costs people an afternoon: results are keyed by the class name, not the pipeline entry name. Everything saves under {base_save_dir}/{class_name}/{experiment_name}/, so GCG-Transfer output appears under results/EnsembleGCG/llama2_7b_vicuna_7b_llama2_13b_vicuna_13b_multibehavior_1000steps/ and no directory named GCG-Transfer exists on disk.

Adding a target model — and the field that gates everything

Pointing HarmBench at your own model means one entry in configs/model_configs/models.yaml. For anything transformers-compatible that is genuinely all it is: a model block passed straight to load_model_and_tokenizer (a model_name_or_path plus whatever overrides that model needs — dtype, trust_remote_code, a chat_template name, explicit pad/eos tokens); a num_gpus for scheduling and vLLM sizing; and model_type. An API model carries the API's model string and a token instead of num_gpus. The shipped file has 35 entries — 21 open_source, 10 closed_source, 3 open_source_multimodal, 1 closed_source_multimodal — with two warts not to copy: mistral-medium misspells its block as mode:, and gpt-4-vision-preview is typed closed_source while the separate gpt4v entry is closed_source_multimodal.

model_type is the field that matters, and it is not advisory. It takes one of four values — open_source, closed_source, open_source_multimodal, closed_source_multimodal — and every entry in run_pipeline.yaml declares an allowed_target_model_types list. A model whose type is not in the list is dropped with a bare continue: no warning, no error, no summary line. Ask for --methods GCG --models gpt-4-0613 and the command exits cleanly having submitted nothing.

That is the mechanical reason the GPT-4 and Claude rows in Table 6 are mostly dashes. It is easy to read a dash as “tried and failed” or “ran out of budget.” Neither: for GCG and its white-box relatives the cell is empty because the method needs gradients through the target and the config refuses to schedule the job. The dash is a claim about the attack's reach, not the model's robustness — precisely why the transfer variants exist as separate columns. (Filter out every requested model in local_parallel mode and the skip surfaces as a bare NoneType traceback in step 2.)

A step-1 job's GPU request is base_num_gpus plus the target's own num_gpus — but only when the entry's experiment_name_template contains <model_name>. Transfer entries, whose experiment name is fixed, get base_num_gpus alone; that is why GCG-Transfer asks for 4 (its four attack models) and never sees the target at generation time. Job count is ceil(num_behaviors / behavior_chunk_size) × len(run_ids) — the arithmetic deciding whether your run is 1 job or 320. Both read off the table below, verbatim from run_pipeline.yaml.

The five MultiModal* rows are the only ones accepting the multimodal types — the enforcement side of the multimodal functional type: a vision model in models.yaml is invisible to the other nineteen methods. And MultiModalPGDBlankImage is not a distinct class, just MultiModalPGD under a different experiment config.

Two entries sit commented out with the same warning, “expensive to run on closed-source models”: HumanJailbreaks-all would use the full jailbreak template library rather than the random_subset_5 the paper reports, and PAP-avg the full 40-strategy persuasion taxonomy rather than the top 5 — each roughly an order of magnitude more API calls per behavior. So the table's Human and PAP-top5 columns are the cheap configurations, not the strongest — worth remembering before reading Human Jailbreaks at 27.3 or PAP-top5 at 16.6 as a ceiling.

The API-only snag: base_url

If your target is behind an HTTP API rather than local weights, HarmBench routes it through api_models.py. That file defines five classes — GPT, GPTV, Claude, Gemini, Mistral — and one dispatch function that picks between them by pattern-matching on the model name string:

def api_models_map(model_name_or_path=None, token=None, **kwargs):
    if 'gpt-' in model_name_or_path:
        if 'vision' in model_name_or_path:
            return GPTV(model_name_or_path, token)
        else:
            return GPT(model_name_or_path, token)
    elif 'claude-' in model_name_or_path:
        return Claude(model_name_or_path, token)
    elif 'gemini-' in model_name_or_path:
        return Gemini(model_name_or_path, token)
    elif re.match(r'mistral-(tiny|small|medium|large)$', model_name_or_path):
        return Mistral(model_name_or_path, token)
    return None

The name is the routing key. No provider field, no endpoint field — a model called gpt-something gets the OpenAI client, full stop. And the OpenAI client is constructed like this:

class GPT():
    API_TIMEOUT = 60

    def __init__(self, model_name, api_key):
        self.model_name = model_name
        self.client = OpenAI(api_key=api_key, timeout=self.API_TIMEOUT)

No base_url. The constructor takes a key and a timeout and nothing else, so it will only ever talk to api.openai.com. That is the snag: a great deal of inference is served over the OpenAI wire format by something that is not OpenAI — a self-hosted vLLM or SGLang server, a vendor's compatible endpoint, a router — and HarmBench cannot be pointed at any of them by configuration. You add a class to api_models.py, or thread a base_url through that constructor and surface it in the model config. A dozen lines, maybe — but a code change, not a YAML edit.

And the failure is quiet. api_models_map returns None when nothing matches, and its only caller, load_generation_function in generate_completions.py, reads that as “not an API model” and falls through to the local-weights branch. So a closed_source entry whose name misses all four patterns does not say “unknown provider” — it hands your API model string to a HuggingFace loader and fails with a missing-repository error. Seeing a hub 404 while wiring up a new endpoint? Check the dispatch function first.

The repo treats this as the extension point rather than a bug — the config docs say new APIs are incorporated in load_generation_function, api_models.py and eval_utils.py. Budget for it; it is the most common reason a run does not start.

The practical shape of a run

Attack cost spans about four orders of magnitude, and the pipeline config is where you read it off. At the cheap end, DirectRequest has no hyperparameters at all: it sends the behavior as-is, produces one test-case set shared by every model (experiment_name_template: default, behavior_chunk_size: all_behaviors, zero GPUs), and the entire cost of the “attack” is writing a JSON file. HumanJailbreaks and ZeroShot are nearly as cheap.

At the expensive end, GCG is 500 optimisation steps at a search width of 512 candidates, one behavior per job (behavior_chunk_size: 1), against each target separately — on the 320-behavior test split, 320 step-1 jobs per model, each doing a quarter of a million forward passes. GCG-Multi multiplies that by five run IDs. This is why the compute bill runs to GPU-months and why the Zenodo archive exists.

So the sensible first move is not --methods all. Run the 80-behavior validation split with DirectRequest end to end, and confirm a plausible ASR comes out before committing GPU time to optimisation.

python ./scripts/run_pipeline.py \
  --methods DirectRequest \
  --models your_model \
  --behaviors_path ./data/behavior_datasets/harmbench_behaviors_text_val.csv \
  --step all --mode local_parallel

harmbench_behaviors_text_val.csv is the right file: the 80 held-out behaviors, spanning all seven semantic categories and all three text functional types, and explicitly the split to iterate against — the test classifier must never be optimised against, so anything you tune belongs on val. Eighty behaviors runs in minutes and is still large enough that a dropped ContextString column or a wrong chat template shows up at once as an implausible number.

That buys four independent checks, one per step: the attack class writes test cases; the merge produces a test_cases.json with the right behavior count; the target loads with the right chat template and returns non-empty completions; the classifier labels them. Each fails differently and each is cheap to fix alone. Then add one black-box attack — PAIR or TAP, both accepting closed-source targets and wanting two GPUs for the attacker — before anything gradient-based touches the cluster.

Then read the number against the grid, not in isolation. DirectRequest averages 25.3 across the paper's 33 targets — a quarter of behaviors need no attack at all — but it is 65.8 on Zephyr 7B and 0.8 on Llama 2 7B Chat. A first run near zero is a safety-trained model behaving as expected, not a broken pipeline; near 60 is also information. And remember what the pipeline does not measure: HarmBench ships no benign set, so a model that refuses everything scores 0% and looks flawless.
