Running it: the four steps

The page that answers “what do I actually type” — and where the runner will quietly refuse to do what you asked.
TL;DR — HarmBench is a dataset you download and a pipeline you run. The behaviors, the classifiers and the copyright hashes ship; the test cases — the actual attack prompts — do not, and you pay for them in GPU hours, one set per (attack × target model) pair. Four scripts do the work: generate_test_cases.py, an optional merge_test_cases.py, generate_completions.py, evaluate_completions.py, chained by scripts/run_pipeline.py in slurm, local or local_parallel mode. The one field that will surprise you is model_type in models.yaml: every method declares which types it accepts, and a model of the wrong type is skipped with a bare continue — no warning, no error, just a missing column. And if your target is an OpenAI-compatible endpoint rather than OpenAI itself, you are patching Python, not editing YAML.

Almost every confusing thing about running HarmBench comes from one split: some of the benchmark is a download, and some of it is a computation. The 510 behaviors are a download. The Llama 2 13B classifier is a download. The 100 MinHash pickles that grade copyright behaviors are a download. The test cases are not. A test case is what an attack produced when it was pointed at a specific model, so there is one set per (method × target model) pair, and producing them is the expensive half of the benchmark. That is why the repo is small and the run is not.

What ships, and what costs you GPU hours

So you have three ways to get a number out, differing by roughly four orders of magnitude in cost. Download the precomputed test cases — the 10.4 GB HarmBench Results 1.0 archive on Zenodo (record 10714577, shipped with the 1.0 release) — and re-run only steps 2 and 3, reproducing the paper's grid or scoring a new model on someone else's attacks. Run only the cheap attacks, which do no optimisation and finish in minutes. Or run the gradient attacks, which is where the GPU-months live.

The middle path works because completions and results are keyed by target model while test cases are keyed by experiment, so any test-case set can be pointed at any model. That is the design, not a hack: it is how GCG-Transfer and TAP-Transfer exist as columns in Table 6, and how closed-model columns get populated by attacks that cannot see closed-model gradients.

The four steps

Four scripts at the repo root, chained by JSON files. Each step reads the previous step's file and writes its own, so knowing the filenames is most of knowing the pipeline — when something goes wrong you diagnose it by finding which file is missing or short.

Step 1 — generate_test_cases.py

This is where the attack actually runs. The script loads a red-teaming class from baselines/, initialises it from configs/method_configs/<Method>_config.yaml, hands it a slice of the behavior CSV, and saves whatever comes back. Everything expensive on this page happens inside that one call: GCG's 500 optimisation steps, PAIR's attacker–target conversation, GPTFuzz's mutation loop.

The slice comes from --behavior_start_idx/--behavior_end_idx, or from an explicit --behavior_ids_subset that overrides them — the right tool for filling gaps after a failed job. Single-behavior methods write to {save_dir}/test_cases_individual_behaviors/{behavior_id}/test_cases.json, alongside a logs.json and a method_config.json recording the exact hyperparameters, the pinned versions of transformers, vllm, ray and fastchat, and any API token masked to its last four characters. That per-behavior config dump is the best provenance feature in the repo.

Step 1.5 — merge_test_cases.py

Step 1.5 exists because of how step 1 is parallelised. The base class states the contract in its docstring: the only requirement on save_test_cases is that running merge_test_cases on the directory afterwards yields a test_cases.json mapping behavior IDs to lists of test cases. Methods with no need to parallelise write that file directly and inherit a merge that is literally pass. Methods that do parallelise — one behavior or a small chunk per job, so a cluster can chew through 320 behaviors at once — scatter output across per-behavior directories, and the merge stitches it back.

Only three classes implement a merge. RedTeamingMethod is the no-op. SingleBehaviorRedTeamingMethod (GCG, PEZ, GBDA, UAT, AutoPrompt) unions the per-behavior directories, asserting no ID appears twice. EnsembleGCG is the interesting one, and the reason its entries carry behavior_chunk_size: all_behaviors: it optimises one adversarial string jointly against every behavior at once, so there is nothing to chunk and nothing to merge along the behavior axis. But it has a second axis. GCG-Multi and GCG-Transfer declare run_ids: [0,1,2,3,4], and the merge concatenates test_cases_{run_id}.json so each behavior ends up with five test cases and an ASR averaged over five independent optimisations. Same script, different seam.

A merge that finds a hole does not complain. SingleBehaviorRedTeamingMethod.merge_test_cases skips any per-behavior file that does not exist, so a job that OOM'd or hit its 24-hour SLURM wall silently drops out of the merged file — and step 3 will happily compute an ASR over whatever survived. Check the length of test_cases.json against your behavior count before trusting a number; notebooks/analyze_results.ipynb exists partly for this.

Step 2 — generate_completions.py

Take the merged test cases, send each to the target model, save what comes back at completions/{model_name}.json. Decoding is greedy and deterministic — do_sample=False on the HuggingFace path, temperature=0 on the vLLM and API paths — and the budget is max_new_tokens=512 for every experiment in the paper.

The code makes the 512 literal in a way the docs only hint at: pass anything else and run_pipeline.py redirects both completions and results into a {N}_tokens/ subdirectory. Non-standard budgets land in a different namespace so they cannot be accidentally averaged with the published grid. It matters because the metric is “did the model produce the harmful artifact,” and an artifact needing 700 tokens to finish scores as a failure at 512.

Step 3 — evaluate_completions.py

The grading pass. It reads the behavior CSV (for tags and context strings) and the completions, then dispatches per behavior: a behavior carrying the hash_check tag goes to MinHash, everything else to the Llama 2 13B classifier, run under vLLM with temperature=0.0, max_tokens=1 — the label is a single token. Output is results/{model_name}.json, one 0/1 label per test case.

Three mechanical details worth carrying. Step 3 re-clips every completion to 512 tokens using the classifier's own tokenizer, truncation_side="right", so even a longer completions file gets graded on its first 512 classifier-tokens. ASR is a mean of means: the fraction of successful test cases is computed per behavior, then those rates are averaged — identical to a flat mean at one test case per behavior, not identical at GCG-Multi's five. And a behavior ID present in the completions but absent from the CSV you passed is skipped with a printed warning, which is how people grade a completions file built from all 400 behaviors against the 80-behavior validation split and wonder why the number moved.

Chaining it: run_pipeline.py

You rarely call the four scripts by hand. scripts/run_pipeline.py reads configs/pipeline_configs/run_pipeline.yaml, expands each method into per-model experiments, works out how many GPUs each job needs, and submits the whole chain:

python ./scripts/run_pipeline.py \
  --methods DirectRequest,PAIR,TAP \
  --models your_model \
  --behaviors_path ./data/behavior_datasets/harmbench_behaviors_text_val.csv \
  --step all --mode local_parallel \
  --cls_path cais/HarmBench-Llama-2-13b-cls

--step takes all, 1, 1.5, 2, 3 or 2_and_3. That last one is the workhorse for anyone using the Zenodo archive: skip generation, score an existing test-case set against a new model. --methods all and --models all expand to every key in the respective config.

--mode takes three values and they are genuinely different execution models, not verbosity levels.

  • slurm — the intended path. Each chunk becomes an sbatch job and the steps are wired together with --dependency=afterok: on the previous step's job IDs, so the whole DAG is submitted in one command and the cluster sorts out the ordering. The hard-coded wall times tell you what the authors expected: 24 hours for step 1, ten minutes for the merge, five hours each for completions and evaluation.
  • local — everything sequentially on this machine. Fine for a smoke test, useless for a real grid. Be aware that steps 1.5, 2 and 3 run under capture_output=True, so in local mode they produce no live output at all — a long silent step 2 is not necessarily a hung one.
  • local_parallel — Ray across the GPUs of a single box, marked experimental in the source. It registers a custom visible_gpus resource sized to torch.cuda.device_count() and sets CUDA_VISIBLE_DEVICES per subprocess, which is a neat way to get cluster-shaped parallelism on one node without installing SLURM. This is the right mode for a single 8×A100 machine.

One path detail that costs people an afternoon: the results directory is keyed by the class name, not the pipeline entry name. Everything is saved under {base_save_dir}/{class_name}/{experiment_name}/, so GCG-Transfer results appear under results/EnsembleGCG/llama2_7b_vicuna_7b_llama2_13b_vicuna_13b_multibehavior_1000steps/ and there is no directory named GCG-Transfer anywhere on disk. The repo's docs call the YAML keys “proper method names” to distinguish them from class names; the filesystem only knows the latter.

Adding a target model — and the field that gates everything

Pointing HarmBench at your own model means one entry in configs/model_configs/models.yaml. For anything transformers-compatible that is genuinely all it is: a model block whose contents are passed straight to load_model_and_tokenizer, containing at minimum a model_name_or_path and optionally the tokenizer and dtype overrides that model needs (use_fast_tokenizer, dtype, trust_remote_code, a chat_template name, explicit pad/eos tokens); a num_gpus used for scheduling and for sizing vLLM; and model_type. For an API model the model block instead carries model_name_or_path (the API's model string) and a token.

The shipped file has 35 entries: 21 open_source, 10 closed_source, 3 open_source_multimodal and 1 closed_source_multimodal. (Two small warts if you are copying from it: the mistral-medium entry's block is misspelled mode: rather than model:, and gpt-4-vision-preview is typed closed_source while the separate gpt4v entry is closed_source_multimodal — the same underlying model reached by two different code paths.)

model_type is the field that matters, and it is not documentation. It takes one of four values — open_source, closed_source, open_source_multimodal, closed_source_multimodal — and every entry in run_pipeline.yaml declares an allowed_target_model_types list. When the runner expands methods against models, a model whose type is not in the method's list is dropped with a bare continue. There is no warning, no error, no summary line. Ask for --methods GCG --models gpt-4-0613 and the command exits cleanly having submitted nothing.

This is the mechanical reason the GPT-4 and Claude rows in Table 6 are mostly dashes. It is easy to read those dashes as “the attack was tried and failed” or “the authors ran out of budget.” Neither is right: for GCG and its white-box relatives the cell is empty because the method needs gradients through the target and the config refuses to schedule the job. The dash is a capability statement about the attack, not a robustness statement about the model — which is exactly why the transfer variants exist as separate columns. (In local_parallel mode the silent skip has a second-order effect worth knowing: if every requested model is filtered out, step 2 ends up calling .values() on a None and you get a NoneType traceback rather than a message telling you the combination was disallowed.)

The GPU count for a step-1 job is base_num_gpus from the table below plus the target model's own num_gpus — but only when the entry's experiment_name_template contains <model_name>. Transfer entries, whose experiment name is fixed, get base_num_gpus alone; that is why GCG-Transfer asks for 4 (its four attack models) and never sees the target at generation time. And the number of step-1 jobs is ceil(num_behaviors / behavior_chunk_size) × len(run_ids), which is the arithmetic that decides whether your run is 1 job or 320.

The five MultiModal* rows are the only ones that accept the multimodal types, which is the enforcement side of the multimodal functional type: a vision model in models.yaml is simply invisible to the other nineteen methods. Two entries in the file are commented out, both with the same warning: “expensive to run on closed-source models.” HumanJailbreaks-all would run the full human jailbreak template library rather than the random_subset_5 the paper reports, and PAP-avg would run PAP's full 40-strategy persuasion taxonomy rather than the top 5. Both multiply the number of API calls per behavior by roughly an order of magnitude against paid endpoints. It is worth knowing that the table's Human and PAP-top5 columns are therefore the cheap configurations of those methods, not their strongest — a caveat when reading Human Jailbreaks at 27.3 or PAP-top5 at 16.6 as the ceiling for those approaches.

The API-only snag: base_url

If your target is behind an HTTP API rather than local weights, HarmBench routes it through api_models.py. That file defines five classes — GPT, GPTV, Claude, Gemini, Mistral — and one dispatch function that picks between them by pattern-matching on the model name string:

def api_models_map(model_name_or_path=None, token=None, **kwargs):
    if 'gpt-' in model_name_or_path:
        if 'vision' in model_name_or_path:
            return GPTV(model_name_or_path, token)
        else:
            return GPT(model_name_or_path, token)
    elif 'claude-' in model_name_or_path:
        return Claude(model_name_or_path, token)
    elif 'gemini-' in model_name_or_path:
        return Gemini(model_name_or_path, token)
    elif re.match(r'mistral-(tiny|small|medium|large)$', model_name_or_path):
        return Mistral(model_name_or_path, token)
    return None

The name is the routing key. There is no provider field, no endpoint field — a model called gpt-something gets the OpenAI client, full stop. And the OpenAI client is constructed like this:

class GPT():
    API_TIMEOUT = 60

    def __init__(self, model_name, api_key):
        self.model_name = model_name
        self.client = OpenAI(api_key=api_key, timeout=self.API_TIMEOUT)

No base_url. The constructor takes a key and a timeout and nothing else, so it will only ever talk to api.openai.com. That is the snag: an enormous amount of inference in 2026 is served over the OpenAI wire format by something that is not OpenAI — a self-hosted vLLM or SGLang server, a cloud vendor's compatible endpoint, a router. HarmBench cannot be pointed at any of them by configuration. You add a class to api_models.py, or you thread a base_url through that constructor and surface it in the model config. Perhaps a dozen lines — but a code change, in a file the pipeline imports, not a YAML edit.

Worse, the failure is not loud. api_models_map returns None when nothing matches, and its one caller, load_generation_function in generate_completions.py, treats None as “not an API model” and falls through to the local-weights branch. So a closed_source entry whose model name does not hit one of those four patterns does not produce “unknown provider” — it produces a transformers or vLLM loader trying to fetch your API model string from the HuggingFace Hub, and an error message about a missing repository that says nothing about the actual problem. If you are wiring up a new endpoint and see a hub 404, look at the dispatch function first.

The repo is upfront that this is the extension point rather than a bug: the config docs say no modification is required for transformers-compatible models, and that new APIs are incorporated in load_generation_function, api_models.py and eval_utils.py. Budget for it. It is the single most common reason a HarmBench run does not start.

The practical shape of a run

Attack cost in HarmBench spans about four orders of magnitude, and the pipeline config is where you can read it off. At the cheap end, DirectRequest has no hyperparameters at all: it sends the behavior as-is, generates one test case set for every model at once (experiment_name_template: default, behavior_chunk_size: all_behaviors, zero GPUs for step 1), and the entire cost of the “attack” is writing a JSON file. Everything after that is just steps 2 and 3, which you have to pay for no matter what you run. HumanJailbreaks and ZeroShot are nearly as cheap.

At the expensive end, GCG is 500 optimisation steps with a search width of 512 candidates per step, one behavior per job (behavior_chunk_size: 1), against every target model separately. On the 320-behavior test split that is 320 step-1 jobs per model, each doing a quarter of a million forward passes on the target. GCG-Multi multiplies by five run IDs. This is why the paper's headline compute figure runs to hundreds of GPU-days and why the Zenodo archive exists.

So the sensible first move is not --methods all. It is: run the 80-behavior validation split with DirectRequest plus one black-box attack, end to end, and confirm you get a plausible ASR out the other side before you commit any GPU time to optimisation.

python ./scripts/run_pipeline.py \
  --methods DirectRequest \
  --models your_model \
  --behaviors_path ./data/behavior_datasets/harmbench_behaviors_text_val.csv \
  --step all --mode local_parallel

harmbench_behaviors_text_val.csv is the right file for this. It is the 80 held-out behaviors, it spans all seven semantic categories and all three text functional types, and it is explicitly the split the authors intend you to iterate against — the test classifier is not to be optimised against, so anything you tune belongs on val. Eighty behaviors is small enough to run in minutes and large enough that a broken ContextString column or a wrong chat template shows up immediately as an implausible number.

That first run buys you four independent checks, one per step: does the attack class initialise and write test cases; does the merge produce a test_cases.json with the right number of behaviors; does the target model load with the right chat template and produce non-empty completions; does the classifier load and label them. Each of those fails differently and each is cheap to fix in isolation. Then add one black-box attack — PAIR or TAP, both of which accept closed-source targets and want two GPUs for the attacker model — to confirm the multi-turn path works before anything gradient-based touches the cluster.

One last calibration. Whatever number comes out, read it against the grid rather than in isolation. DirectRequest averages 25.3 across the paper's 33 targets — a quarter of behaviors need no attack at all — but it is 65.8 on Zephyr 7B and 0.8 on Llama 2 7B Chat. If your first DirectRequest run comes back near zero, that is a safety-trained model behaving as expected, not a broken pipeline; if it comes back near 60, that is also information. And remember what the number is not measuring: HarmBench ships no benign set, so a model that refuses everything scores 0% and looks flawless. The pipeline will never tell you that.
